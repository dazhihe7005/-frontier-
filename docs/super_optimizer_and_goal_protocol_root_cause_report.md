# SUPER 局部轨迹优化与目标协议根因报告

## 1. 结论摘要

本轮把此前混在一起的轨迹异常拆成了两个彼此独立的问题：

1. **官方 SUPER 的热启动时间分配会生成退化的极短轨迹段。** 安全走廊内部点和轨迹终点
   可能映射到同一个导引轨迹采样点，使原始时间差为 0。官方代码先把它钳为 0.01 s，随后
   又统一乘以 0.8，形成 0.008 s 初值。该退化段会把加速度、角速度和推力需求放大，直接
   触发指数轨迹优化失败。
2. **任务一和 SUPER 之间缺少“撤销目标/进入空闲”的明确协议。** 高层决策器进入
   `WAIT_MAP_CLOSURE` 时已经没有活动目标，PX4 桥会正确地改为当前位置悬停；但官方 SUPER
   仍保留最后一个目标，并在旧轨迹结束后继续对它执行 `PlanFromRest`。这会造成“飞机悬停，
   规划器却继续规划旧目标”的状态分裂。

第一个问题已由同场景运行时诊断建立直接因果证据；第二个问题已由话题录包、运行状态和三层
源码控制流共同确认。二者都不是提高惩罚权重、扩大高度围栏或放宽安全距离能够正确解决的参数
问题。

## 3. 问题一：官方热启动时间分配产生 8 ms 退化段

### 3.1 表面现象

长时间优化器诊断中，约束失败并不是单一类型：

- 共记录 268 次通用约束失败警告；
- 262 次超过加速度判据；
- 258 次超过推力判据；
- 77 次超过角速度判据；
- 7 次超过位置判据；
- 其中 70 次的优化结果含小于 0.02 s 的分段，最小值约 0.00815 s。

代表性失败的优化时间为 `0.7136 s + 0.00819 s`，同时加速度违规量约 349.4、角速度
违规量约 197.6、推力违规量约 115.8。继续增大惩罚权重只是在要求优化器用一个几乎零时长的
分段完成有限空间运动，并不会消除错误输入。

另外还存在独立的 L-BFGS 线搜索失败：最初一次 `PlanFromRest` 的位置、加速度、角速度和推力
违规量都为 0，却因线搜索达到最大尝试次数而失败。因此不能把所有 `GenerateExpTrajectory`
失败归为同一个原因。

### 3.2 源码数据流

`ExpTrajOpt::processCorridorWithGuideTraj()` 对每个安全走廊重叠区域求一个吸引点，然后独立寻找
离该吸引点最近的导引轨迹采样点：

```cpp
min_id[j] = i;
time_stamps(j + 1) = opt_vars.guide_t[i];
```

终点时间则直接固定为导引轨迹最后时间：

```cpp
time_stamps(last) = opt_vars.guide_t.back();
```

源码没有要求相邻 `min_id` 严格递增，也没有禁止最后一个走廊吸引点使用导引轨迹最后采样点。
当它和终点映射到同一点时：

```cpp
raw_dt = time_stamps(last) - time_stamps(last - 1) = 0
```

随后官方实现执行：

```cpp
opt_vars.times = max(0.01, raw_dt);
opt_vars.times *= 0.8;
```

所以退化段初值必然为：

```text
0.01 s × 0.8 = 0.008 s
```

这与运行日志反复出现的约 0.00815 s 优化结果具有明确的数值对应关系。

### 3.3 同场景运行时因果证据

一次性诊断在应用 10 ms 下限前打印 `min_id`、`time_stamps` 和原始时间差。同一次短时仿真中：

- 共出现 5 次 `DIAG_GUIDE_TIME_ALIAS`；
- 共出现 5 次优化约束失败；
- 每一次诊断后紧接着同一次重规划的优化失败；
- 5 次的 `raw_dt` 全部为 0；
- 例如 `guide_size=16`、`min_id=15`，内部点时间与终点时间均为
  `1.742166080454276 s`；
- 内部走廊吸引点距该最后采样点约 0.40 m，不是数学上可忽略的同一点。

因此因果链已经闭合：

```text
安全走廊内部点独立匹配最近导引采样点
  → 最后内部点与终点使用同一时间戳
  → 原始分段时间为 0
  → 官方下限和 0.8 缩放生成 0.008 s 初值
  → 动力学需求异常放大
  → 加速度/角速度/推力约束失败
```

这不是任务一 frontier 选点、Fast-LIO2 坐标系或 PX4 跟踪造成的数值巧合；故障在轨迹送给 PX4
之前已经发生。

### 3.4 为什么此前有些重规划仍能成功

该缺陷不是每次必触发。安全走廊数量、重叠区域吸引点、导引轨迹采样和当前重规划时刻改变后，
内部点可能映射到不同采样索引；此时分段时间严格为正，优化可以成功。因此日志会交替出现
`ReplanOnce succeed` 和约束失败。这种间歇性不代表参数接近正确，而是退化输入只在特定走廊
几何关系下产生。

### 3.5 单变量修复与同场景 A/B 结果

已按测试先行方式实现时间初始化修复。修复不改目标点、走廊、碰撞约束、速度配置、惩罚权重或
返航条件，只在 `init_path` 已经形成后，为每个实际非零空间段加入
`segment_distance / max_vel` 的几何时间下界；原有时间更长时保持不变，零长度段也不被任意放大。
这使导引轨迹最近时间只作为热启动参考，不能再要求一个有限长度空间段在 8 ms 内完成。

测试过程先证明新增用例在实现前因缺少接口而失败，随后实现并通过七个用例：0.4 m/0.008 s
退化段被提升到0.4 s，已有0.75 s时间保持不变，零长度段保持原时间；非有限路径、非有限时间、
负时间、非法速度和维度不匹配会显式返回失败。Release 构建成功，7项测试全部通过。

独立代码审查还发现显式 `init_ps/init_ts` 重载原先会在公共初始化之后重新覆盖时间。正式补丁已在
该覆盖之后按显式路径再次施加同一几何下界，并把最小时间检查移到覆盖之后；因此公开重载不能再
绕过修复。异常输入沿用SUPER的失败返回路径，不抛出未捕获异常终止ROS节点。
最终独立复审未发现Critical或Important问题；剩余非阻塞测试缺口是尚未为显式初值公开重载建立
端到端集成用例，当前已有源码顺序检查和共享时间下界单元测试覆盖。

在相同40×40×30 m、30 m仿真雷达场景中，临时诊断再次捕获5个原始0.008 s退化段，实际段长为
0.166～0.534 m；它们被修正为相应的0.166～0.534 s后，规划继续成功。同一次运行到约103 s：

- 几何时间下界触发5次；
- `Opt failed, Omg or thr or Pos violation` 为0次；
- `Line search reaches` 为0次；
- `GenerateExpTrajectory SUCCESS` 36次；
- `Traj finish` 35次。

取证基线短时运行中则是5次重复时间戳诊断紧跟5次同类约束失败。两次运行时长不同，所以不能把
总成功次数直接当作成功率对比；有意义的证据是修复版再次真实遇到5个0.008 s输入，而5个都没有
再触发对应约束失败。临时诊断打印已删除，正式代码只保留时间下界和回归测试。

## 4. 问题二：任务层悬停与 SUPER 旧目标重规划并存

### 4.1 运行时证据

话题录包显示，在高层状态持续为 `WAIT_MAP_CLOSURE` 时：

- `/planning/pos_cmd` 仍有 SUPER 输出；
- `super_px4_command_bridge` 的状态是 `HOLD_COMMAND_TIMEOUT`；
- `/mine_uav/setpoint_cmd` 发布当前位置、零速度和零加速度悬停；
- PX4 保持 `OFFBOARD` 且已解锁；
- SUPER 保留的最后目标约为 `(5.996, 0.511, 1.505)`。

因此不是 SUPER 没有输出，也不是 PX4 不接收，而是桥接器根据高层“当前无活动目标”状态主动
丢弃旧规划输出并保持位置。

### 4.2 三层控制流

高层决策器在目标到达、滚动交接、阻塞抢占或超时后会令 `have_active_goal_=false`。如果已经看到
前方边界但地图闭合条件尚未稳定，它发布 `WAIT_MAP_CLOSURE` 并且不发布新 `/goal`。

项目桥接器把 `WAIT_DATA`、`WAIT_GOAL`、`WAIT_FRONTIER`、`WAIT_MAP_CLOSURE`、
`WAIT_MODEL_COVERAGE` 和 `DISABLED` 视为悬停状态，将 `valid_command_` 清零。这是合理的飞行安全
意图：没有有效高层目标时不能继续盲目执行历史轨迹。

但官方 SUPER 只订阅新的目标位置，没有目标撤销或空闲输入。旧轨迹结束后，它只有两个选择：

- 实际位置距旧目标小于硬编码 0.1 m：转入 `WAIT_GOAL`；
- 否则：转入 `GENERATE_TRAJ`，继续对旧目标执行 `PlanFromRest`。

所以当前接口实际形成：

```text
决策器：当前没有活动目标
桥接器：忽略规划输出，保持当前位置
SUPER：旧目标仍有效，继续重规划
```

这会制造重复 `Traj finish → PlanFromRest`、无效优化负载和状态认知分裂。它不是简单删除桥接器
悬停保护就能解决的问题；那样会让无人机继续飞向已被上层撤销的历史目标。

## 5. 与 ROGMap 别名缺陷的关系

此前报告确认官方 SUPER 内置 ROGMap 存在输入/输出别名缺陷，但 165 s 运行时诊断中目标返回
位置始终不变，异常事件为 0，而轨迹优化失败仍持续发生。因此：

- ROGMap 别名缺陷是真实的独立安全缺陷；
- 它不是本报告这批优化失败的已证实原因；
- 本轮 8 ms 退化段已经有自己的直接运行时因果证据。

## 6. 正确修复边界

### 6.1 轨迹时间初始化

该项已采用最小物理约束修复：对 `head → 各实际优化中间点 → tail` 的每一段，令初始化时间不小于
`段长 / max_vel`。它不是把0.01 s替换成另一个任意常数，也不改变安全走廊几何；即使导引时间戳
重复，实际非零空间段也会获得与配置速度量级一致的初值。补丁保存在
`patches/super_geometric_time_lower_bound.patch`。

该下界是平均速度的必要条件，不是对加速度、端点速度和高阶动力学可行性的充分证明；这些仍由
原优化器处理。因此本修复可以被认定为关闭了8 ms退化输入链，但不能被扩大解释为“所有SUPER
优化问题已解决”。若后续仍在非退化时间输入上出现同类失败，应单独记录并分析，不得继续叠加
经验常数。

### 6.2 目标生命周期协议

任务层与 SUPER 之间需要一个明确且唯一的契约，例如增加 `ACTIVE / HOLD / CANCELLED` 状态或
取消目标接口。验收要求为：

1. 高层有活动目标时，SUPER 才允许规划和重规划该目标；
2. 高层撤销目标后，SUPER 清除旧目标并停止 `PlanFromRest`；
3. 桥接器在取消确认前继续安全悬停，不能执行旧指令；
4. 发布新目标时使用目标序号，防止旧轨迹和新状态乱序；
5. CH7 退出、传感器失效、等待地图闭合和任务完成都走同一取消/保持状态机。

## 7. 当前安全状态

8 ms退化段修复已经写入当前运行工作区，并以回归测试、Release编译和同场景运行时触发验证。
临时诊断已撤销，仿真和11312 ROS Master均已停止。

这不等于任务一已经满足有桨自主飞行条件。仍需独立解决高层无活动目标时SUPER保留旧目标的取消
